# Install sk

Instructions for an agent. Set up [sk](https://github.com/ivorpad/sk) so that it is the only skill the user's agents load, and every other skill loads on demand.

1. Check `node --version` is 18 or later. Stop and tell the user if not.
2. Install sk where it's missing. For Claude Code, skip this if `claude plugin list` shows `sk@sk`; otherwise install the plugin: `claude plugin marketplace add ivorpad/sk`, then `claude plugin install sk@sk`. With the plugin in place, a `~/.claude/skills/sk` from an earlier `npx skills add` loads a second copy: tell the user and remove it once they agree. For any other agent, skip this if its skills folder already has sk; otherwise `npx skills add ivorpad/sk -g -y`.
3. Use `~/.skills` as the skill library, unless SKILLS_HOME is already set; then use that. Create the folder if it's missing.
4. Find every skill installed outside the library: each folder holding a SKILL.md directly under ~/.claude/skills, ~/.agents/skills, ~/.codex/skills, ~/.cursor/skills and ~/.copilot/skills, following symlinks. Skip sk itself. Skip anything managed elsewhere: plugin caches, ~/.codex/skills/.system, and ~/.claude/skills/synced (claude.ai sync). Skip skills committed inside project repositories.
5. Show the user the list: name, where it is, and whether the library already has a skill of that name. Ask before moving anything.
6. Back up every folder you will change into one dated tar.gz under the user's home directory, and tell them its path.
7. Copy each skill into the library as <library>/<name>/, following symlinks and skipping .git, node_modules, .venv and __pycache__. When the library already has that name with different content, keep the copy whose SKILL.md was modified most recently, and list what you dropped.
8. Only after every copy is verified, remove the originals from the agent folders, leaving sk.
9. If the library isn't ~/.skills, make SKILLS_HOME stick: add `export SKILLS_HOME="<library>"` to the user's shell profile (~/.zshenv for zsh, ~/.bashrc for bash, `setx SKILLS_HOME "<library>"` on Windows), and add it under "env" in ~/.claude/settings.json if they use Claude Code.
10. If ~/.claude/settings.json has "skillOverrides" entries for skills you moved, tell the user. They can stop sk loading those skills natively, and removing them is the user's call.
11. Verify: list each agent skill folder (it should hold only sk, or nothing besides plugin-managed folders when sk is the plugin), then run `node <sk folder>/scripts/sk.mjs find <a word from one moved skill>` and show the user the output.
12. On Claude Code, offer the `/` autocomplete: typing `/` and part of a library skill's name lists it as `/lib:<name> (MCP)`, and picking it loads that skill. It runs `sk.mjs mcp` as an MCP server, and adding one edits the user's Claude Code config. Read the state first with `claude mcp get lib` and `claude mcp get sk`. They only read, and exit 1 with `No MCP server named …` when there is none. If `lib` is `Connected` and its `Args:` line ends in `sk.mjs mcp` without `plugins/cache/` in the path, it is already set up, so go to step 16. Otherwise ask the user once, saying what you will add and what you will remove, and go to step 16 if they decline.
13. Pick the name and the path. The name is `lib`, never `sk`: every entry carries the server name, so one called `sk` buries the real `/sk` under the whole library. The path has to survive updates, so use whichever of these files exists: `<config>/skills/sk/scripts/sk.mjs`, or for the plugin `<config>/plugins/marketplaces/sk/skills/sk/scripts/sk.mjs`. `<config>` is the profile's config folder, `$CLAUDE_CONFIG_DIR` if set and `~/.claude` if not. Never use the plugin's `plugins/cache/sk/sk/<version>/` copy, which moves on every update. If neither file exists, skip the autocomplete and say so.
14. Register it. First remove what is in the way, now that the user has agreed. An `sk` server whose `Args:` line ends in `sk.mjs mcp` is an older sk, and a `lib` that isn't `Connected` or points into `plugins/cache/` is stale. Use the command printed at the end of each `get` output (`claude mcp remove sk -s user` for user scope), and leave an `sk` server that runs something else. Then run `claude mcp add -s user lib -- node <absolute path> mcp`. It edits the config of the profile its environment names and prints a `File modified:` line, so check that the line names the profile you meant. Run it in the profile the user is working in. For another profile they name, repeat steps 12 to 15 without asking again, with `CLAUDE_CONFIG_DIR=<its folder>` set on each command (unset for the default `~/.claude` profile) and `<config>` worked out from it. The server finds the library through `SKILLS_HOME` (Claude Code passes its own environment on, and step 9 makes it stick) or `~/.skills`, so add `-e SKILLS_HOME=<library>` straight after `lib` only if the library lives elsewhere and the user declined step 9.
15. Run `claude mcp get lib` and expect `Status: ✔ Connected`. That shows the server starts, not that it found the library, so also run `node <absolute path> index --check` and expect a line like `620 skills in 24 categories`. Exit code 1 there only means the index files are stale. `sk: no library at …` means the server would list nothing, so fix step 3 or 9 first. Tell the user to open a new Claude Code session, since a running one may not have the server, and to type `/` plus part of a library skill's name there. Tell them that text typed after the name is dropped, so they ask for what they want in the next message.
16. Report what moved, what you skipped and why, the backup path, whether you set up the autocomplete and for which profiles, and anything still loading that you couldn't move.
